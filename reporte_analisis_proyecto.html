Sistema propio con hash scrypt / PBKDF2, cookies seguras HttpOnly, tokens SHA-256 en BD y 3 roles diferenciados (consulta, coordinador, admin).

Script de Diagnóstico 🛠️

Script verificar_instalacion.py que valida archivos, sintaxis, dependencias, escritura en disco y realiza pruebas unitarias de creación de usuarios en SQLite temporal.

🔄 Diagrama de Flujo de Componentes Funcionales

El siguiente diagrama ilustra el flujo de datos integral de la plataforma: desde el acceso y validación criptográfica, pasando por los motores analíticos deterministas y de inteligencia artificial, hasta la persistencia y exportación.

Desglose de los Canales Funcionales

Canal 1: Asistente Determinista ✦

Garantiza que ninguna cifra provenga de alucinación:

  1. El usuario envía una consulta en lenguaje coloquial (ej. "¿Dónde estuvo más cerrado el voto en Valles?").
  2. Groq interpreta la intención y devuelve un Plan JSON estructurado.
  3. Catalogo.resolver valida entidades con rapidfuzz (umbral WRatio 72%).
  4. Se compila una consulta SQL con marcas de sustitución ? (evita inyección SQL).
  5. Pandas ejecuta la consulta en data/electoral.db y calcula los márgenes de forma exacta.
Canal 2: Perfil Territorial ⌖

Genera la radiografía electoral y de campaña de cualquier demarcación:

  1. Selección dinámica o navegación por enlace permanente (#territorio/municipio/MATEHUALA).
  2. Cálculo de participación: votos_emitidos / LISTA_NOMINAL.
  3. Clasificación de competitividad (desde Empate exacto hasta Ventaja amplia).
  4. Identificación de las secciones más disputadas de la demarcación.
  5. Genera la FICHA DE DATOS VERIFICADOS que alimenta al módulo de discursos.
Canal 3: Discursos y Auditoría ✍️

Redacción asistida con control de calidad cuantitativo:

  1. Selección de formato (Mitin, Debate, WhatsApp, Boletín) y demarcación.
  2. El LLM recibe la ficha de datos oficiales con instrucción estricta de no inventar números.
  3. Al recibir el borrador, el motor regex de redaccion.py extrae todas las cantidades.
  4. Se cotejan contra la ficha: las cifras no encontradas se marcan en rojo como no_respaldadas.
  5. El botón "Corregir cifras" reinicia el prompt instruyendo al LLM a subsanar únicamente los datos dudosos.
Canal 4: Semáforo y Operación ◉

Monitoreo mediático y control de ejecución de campaña:

  1. Búsqueda temporal vía SerpAPI y extracción del contenido editorial con Trafilatura.
  2. Clasificación de tono (positivo, neutro, negativo) con LLM o fallback léxico SpaCy.
  3. Tablero Kanban con tareas asociadas a metas territoriales, peso relativo (1 a 8) y prioridades.
  4. Generación de informes ejecutivos en PDF de alta calidad mediante ReportLab.

🛡️ Modelo de Seguridad, Autenticación y RBAC

La implementación en backend/auth.py incorpora prácticas alineadas con los estándares OWASP:

1. Criptografía y Sesiones

  • Hashing adaptativo: Utiliza scrypt (N=16384, r=8, p=1) por defecto. Si OpenSSL no dispone de scrypt, degrada de forma segura a PBKDF2-HMAC-SHA256 con 600,000 iteraciones.
  • Protección contra Timing Attacks: Cuando se consulta un usuario inexistente, se ejecuta _hash_falso() para mantener un tiempo de respuesta constante y evitar la enumeración de usuarios.
  • Manejo de Tokens: Las cookies sesion_ie almacenan un token aleatorio criptográficamente seguro (secrets.token_urlsafe(32)). En la base de datos solo se almacena su huella SHA-256.
  • Cabeceras y Flags: Cookies con HttpOnly, SameSite=Lax y soporte de COOKIE_SECURE=1 para HTTPS en producción. Cabeceras HTTP automáticas: X-Content-Type-Options: nosniff, X-Frame-Options: DENY y Referrer-Policy: same-origin.

2. Matriz de Roles y Permisos (RBAC)

Bloqueo por Fuerza Bruta (Rate Limiting) El backend bloquea intentos tras 8 fallos por usuario o 30 por IP en una ventana de 10 minutos (600 s). Nota técnica: Este contador reside actualmente en la memoria del proceso, por lo que en entornos con múltiples trabajadores (multi-worker uvicorn) requerirá persistirse en SQLite o Redis.

📦 Análisis Detallado de Módulos Funcionales

1. Asistente Electoral (asistente_electoral.py)

Principio clave: El LLM interpreta la pregunta, pero Python calcula y ejecuta.

El modelo de lenguaje nunca genera código SQL directamente. El proceso sigue un estricto pipeline:

  1. El usuario envía una consulta en lenguaje natural (ej. "¿Quién ganó en Matehuala y con qué diferencia?").
  2. El LLM devuelve un Plan JSON estructurado con dimensiones, filtros y métricas.
  3. Catalogo.resolver valida cada entidad geográfica o política usando distancia difusa (RapidFuzz WRatio) contra el catálogo maestro de San Luis Potosí (umbral de coincidencia: 72%).
  4. Se genera una consulta SQL parametrizada protegida contra inyección SQL.
  5. Los cálculos de porcentajes y márgenes se realizan en memoria con Pandas de forma determinista.

2. Perfil Territorial (territorio.py)

Genera fichas integrales para cualquier unidad territorial (Estado, Municipio, Distrito Local, Distrito Federal, Sección).

  • Métricas de Votación: Votos emitidos, nulos, no registrados y lista nominal.
  • Cálculo de Porcentaje: votos_opcion / TOTAL_VOTOS_CALCULADOS * 100.
  • Participación Ciudadana: votos_emitidos / LISTA_NOMINAL * 100.
  • Clasificación de Competitividad: Empate exacto (margen = 0), Muy reñida (< 3 pp), Competida (< 8 pp), Ventaja clara (< 15 pp), Ventaja amplia (≥ 15 pp).
  • Calidad de Datos: Alerta automática si la suma de opciones difiere del total calculado en la base.
  • Integración con Campaña: Vincula metas específicas asignadas a dicho territorio.

3. Resultados Gráficos (resultados_graficos.py)

Módulo de visualización comparativa que permite analizar tendencias temporales, voto diferenciado entre cargos (Presidencia vs. Alcaldía vs. Diputaciones) y simulación de coaliciones políticas con cálculo automático de porcentajes agrupados.

4. Semáforo de Posicionamiento (posicionamiento.py & informes.py)

Monitoreo de prensa mediante SerpAPI y Trafilatura. Realiza análisis de tono (positivo, neutro, negativo) y encuadres temáticos. Incluye soporte para comparación lado a lado de dos figuras públicas y exportación de reportes ejecutivos en PDF de alta calidad tipográfica mediante ReportLab.

5. Campaña y Tareas (campania.py)

Tablero ejecutivo y Kanban para la gestión operativa:

  • Estructura jerárquica: Áreas ➔ Personas ➔ Metas (con indicador y objetivo numérico) ➔ Tareas.
  • Ponderación: Tareas con prioridad (baja, media, alta, crítica) y peso (1 a 8) para medir el avance real de las metas.
  • Modo Demo: Sembrado y limpieza automática de datos de prueba para entrenamiento de equipos.

✍️ Verificación de Cifras en Discursos (Anti-Alucinación)

Una de las innovaciones más destacadas de la plataforma es el subsistema en backend/redaccion.py. Resuelve el riesgo común donde un modelo de lenguaje "inventa" estadísticas creíbles pero falsas.

Flujo de Auditoría de Cifras ⚙️
  1. El usuario selecciona un territorio (ej. Municipio de Matehuala).
  2. El backend genera una FICHA DE DATOS VERIFICADOS con cifras oficiales de la base SQLite.
  3. El prompt del sistema instruye al LLM a usar únicamente esas cifras.
  4. Al recibir el borrador, una expresión regular extrae todos los números, porcentajes y cifras > 100.
  5. Se cotejan contra los datos oficiales y lo redactado por el usuario.
  6. Las cifras que no coinciden se catalogan como no_respaldadas.
Ajuste Automático: "Corregir Cifras" 🔄

Si el frontend detecta cifras dudosas, habilita el botón especial Corregir cifras.

Al hacer clic, el sistema reescribe el prompt inyectando explícitamente la lista de valores dudosos detectados: 

instruccion = ("Reescribe el texto corrigiendo las cifras "
               "que no coinciden con los datos... "
               f"Cifras a corregir: {dudosas}.")

Las exportaciones a Word y PDF adjuntan una tabla con el sello de auditoría de cifras.

🗄️ Arquitectura de Persistencia y Bases de Datos

La información se distribuye en tres bases de datos SQLite dentro del directorio data/:

1. electoral.db 🗳️

Propósito: Datos electorales históricos.

Ciclo de vida: Se descarga y regenera al iniciar la aplicación si se conecta a Google Sheets.

Contenido: Tabla resultados con índices normalizados en __norm_entidad, __norm_municipio, etc.

2. campania.db 📋

Propósito: Planificación estratégica de la campaña.

Ciclo de vida: Persistente. Cuenta con migraciones no destructivas automáticas.

Tablas: areas, personas, metas, tareas.

3. plataforma.db 👥

Propósito: Usuarios, sesiones y contenido generado.

Ciclo de vida: Persistente. Crítico para la operación del sistema.

Tablas: usuarios, sesiones_auth, discursos, discurso_mensajes.

Esquema DDL de plataforma.db (Usuarios & Historial)

CREATE TABLE usuarios (
    id INTEGER PRIMARY KEY,
    usuario TEXT NOT NULL UNIQUE COLLATE NOCASE,
    nombre TEXT NOT NULL DEFAULT '',
    clave_hash TEXT NOT NULL,
    rol TEXT NOT NULL CHECK (rol IN ('admin', 'coordinador', 'consulta')),
    activo INTEGER NOT NULL DEFAULT 1,
    creado TEXT NOT NULL,
    ultimo_acceso TEXT
);

CREATE TABLE sesiones_auth (
    token_hash TEXT PRIMARY KEY,
    usuario_id INTEGER NOT NULL REFERENCES usuarios(id) ON DELETE CASCADE,
    creado TEXT NOT NULL,
    expira TEXT NOT NULL
);

CREATE TABLE discursos (
    id INTEGER PRIMARY KEY,
    usuario_id INTEGER NOT NULL REFERENCES usuarios(id) ON DELETE CASCADE,
    titulo TEXT NOT NULL DEFAULT 'Nuevo discurso',
    formato TEXT NOT NULL DEFAULT 'libre',
    territorio TEXT,
    creado TEXT NOT NULL,
    actualizado TEXT NOT NULL
);

CREATE TABLE discurso_mensajes (
    id INTEGER PRIMARY KEY,
    discurso_id INTEGER NOT NULL REFERENCES discursos(id) ON DELETE CASCADE,
    rol TEXT NOT NULL CHECK (rol IN ('user', 'assistant')),
    contenido TEXT NOT NULL,
    verificacion TEXT,
    creado TEXT NOT NULL
);

⚖️ Evaluación Técnica y Recomendaciones de Mejora

Alerta Crítica de Seguridad: Claves en .env.example El archivo .env.example del proyecto contiene claves que parecen reales de GROQ_API_KEY y SERPAPI_KEY.
Acción inmediata requerida: Revocar estas claves en los paneles de Groq y SerpAPI y sustituirlas en .env.example por textos de marcador de posición como GROQ_API_KEY=tu_clave_aqui.
Advertencia de Entorno Local: .venv creado en macOS Se detectó que el directorio .venv actual contiene enlaces simbólicos apuntando a /Library/Developer/CommandLineTools/usr/bin/python3 (ruta de macOS). Al ejecutar en un entorno Linux, este entorno virtual no funcionará.
Solución: Recrear el entorno virtual en la máquina Linux ejecutando: 
python3 -m venv .venv --clear
source .venv/bin/activate
pip install -r requirements.txt
python verificar_instalacion.py
Puntos Fuertes Destacados ⭐
  • Prevención de Inyección SQL y Alucinación: Arquitectura determinista de dos pasos (Intención JSON ➔ SQL Parametrizado).
  • Frontend Ultraligero: Sin dependencias de Node.js/npm; el servidor FastAPI entrega directamente los archivos estáticos optimizados.
  • Degradación Elegante: Respaldo léxico si falla el LLM; modelo SpaCy sentencizer básico si no hay descarga del modelo completo; compatibilidad con LibreSSL mediante PBKDF2.
  • Separación Estricta de Roles: Permisos validados en el backend mediante dependencias de FastAPI (Depends(auth.requiere("..."))).
Oportunidades de Mejora para Producción 📈
  • Despliegue Multi-Worker: El control de intentos fallidos de login (rate limiting) está en memoria; para producción con múltiples workers de Uvicorn, debe trasladarse a una tabla SQLite o Redis.
  • Módulo Cartográfico: La pestaña cartografia continúa como placeholder. Se puede implementar rápidamente con Leaflet.js consumiendo archivos GeoJSON de las secciones electorales del INE/CEEPAC.
  • Pruebas Automatizadas: Aunque existe verificar_instalacion.py, convendría añadir una suite con pytest para validar cálculos electorales y endpoints ante cambios futuros.
  • Persistencia de Sesiones de Chat: Las instancias de AsistenteElectoral en memoria expiran por TTL (3h), pero un reinicio del servidor borra el contexto de la conversación activa del asistente.
